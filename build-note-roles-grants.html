Roles vs Admin Grants — the separation contract, on one page

What the backend must guarantee about roles, admin grants, and how the two combine into effective access. Everything here is already true in the prototype and asserted by the test suites — this note is the contract, the flow chart is the runtime check.

1Two disjoint worlds — zero shared permissions

A role says what a person does day to day. A grant says what they administer. They are built from different permission sets and share no permission tag — verified by intersection over the live model.

At most one per person, on top of the role · People Admin · Technical Admin · Full Site Admin

🧩 The 8 product modules cut across both worlds on purpose: one plant licence flag caps the operate side and the configure side of a feature together.
Full Site Admin = People + Technical, exactly — implement it as the union of the other two grants, never as a third permission list that could drift.
Global Admin is the one deliberate exception — the superuser: all 10 sets everywhere, including the 3 exception permissions. Its check never returns “no”. It overlaps every role by design; don't “fix” that.

2Same module, both sides — operate vs configure, never the same permission

Where people expect overlap, it's actually this pattern: roles operate a feature, grants configure it, and the module licence gates both at once.

Near-miss pairs that are different permissions despite similar names: approve.assign (give someone a task) ≠ people.rosters (build the shift schedule) · readplant.dash (view dashboards) ≠ tech.dashcfg (build them) · work.inventory (use stock) ≠ tech.stores (define the catalog).

3The runtime check — one flow, every request

For any user U, permission P, plant X — evaluate top to bottom, stop at the first hit. Compute it fresh on every check; never trust a snapshot stored at assignment time.

STEP 1 · THE CEILINGIs P's module licensed at plant X? (flag on the plant record)
→
NO → DENYcapped ▢ — P stays saved on the profile and re-activates if X licenses the module. Never delete it.
↓ licensed — continue
STEP 2 · SUPERUSERDoes U hold the Global Admin grant?
→
YES → ALLOWsuperuser — audited, never denied
↓ not Global — continue
STEP 3 · EXCEPTION PERMISSIONSIs P one of the 3 exceptions — remote.actuate, flags.impersonate, flags.sensorhealth?
→
YES + explicit grant → ALLOWone person + one plant + one written reason (impersonate also needs the People set)
YES, no grant → DENYnever via a role default or any bulk action
↓ an ordinary permission — continue
STEP 4 · PER-PLANT OVERRIDEDoes U have an override for P at plant X? (reasoned, audited, counted as drift)
→
ADDED ✚ → ALLOWbeats the standard
REMOVED ⊘ → DENYbeats the standard
↓ no override — fall back to the standard
STEP 5 · THE STANDARDIs P's set in U's role (work / approve / oversight / readplant / portfolio) or U's grant (people / tech)?
→
YES → ALLOWstandard ✓ — disjoint worlds, so exactly one of the two supplies it
NO → DENYnot granted −

The same five states drive the Access-review cells: ✓ standard · ✚ added · ⊘ removed · ▢ capped · − not granted. Amber always means a reasoned deviation; grey always means the module isn't licensed.

4Build rules to enforce (assert these, don't just document them)

  • Role definitions may only reference work, approve, oversight, readplant, portfolio. People/Technical/Full Site may only reference people, tech. A role touching an admin set — or vice versa — is a bug, not a configuration.
  • The catalog is closed: exactly 5 roles + 4 grants, no custom roles, no role-creation or role-editing endpoint for anyone (People Admins included).
  • One role per user (account-wide) and at most one grant. The save payload is {userId, role, grant, assignments:[{plant, company, overrides, reason, drift}], entitlementContext} — no role on assignment rows, and entitlementContext is informational only.
  • Every override and every exception carries a written reason and lands in the audit log; bulk actions skip sensitive permissions and report every skip.
  • Full Site = union(People, Technical) computed, not copied. Global = everything, checked first, never filtered.
  • Run node tests/verify-usercenter.js — the suites already assert the disjointness, the closed catalog, the payload shape, the ceiling, and the exception rules against the prototype.
